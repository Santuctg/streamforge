# StreamForge v12.82 — Hardened trust boundaries

## What changed

This release closes the review's widest trust boundaries: what a Panel role
can make the servers read, who can disconnect viewers, and who can mint Node
credentials.

- **Channel sources must be transport URLs.** `file:`, `concat:`, `lavfi:`,
  `ftp:` and plain local paths are refused when a channel is saved *and*
  when FFmpeg or ffprobe opens it, because such a source reads host files and
  can play them out as a live stream. `http(s)`, `rtmp(s)`, `rtsp(s)`, `rtp`,
  `udp`, `tcp`, `srt`, `mmsh/t` and `ws(s)` keep working; unusual schemes go
  into `STREAMFORGE_SOURCE_SCHEME_ALLOWLIST`, local files need
  `STREAMFORGE_ALLOW_LOCAL_FILE_SOURCES=1`. A refused source becomes a normal
  channel error with a log entry.
- **Killing a viewer session needs `sessions.kill`**, not just
  `dashboard.view`, and every kill is written to the audit log. Roles that
  already had `dashboard.view` receive the new permission automatically once,
  so nothing stops working on upgrade; afterwards grant or revoke it per role
  under **Roles & Permissions**.
- **Node API tokens can be rotated from the Panel.**
  **Nodes → Regenerate API token** (needs `nodes.edit`) mints a fresh token,
  rewrites `STREAMFORGE_NODE_TOKEN` in the Node's `/etc/streamforge-node.env`
  over saved SSH, restarts the Node Agent and only then stores the new value,
  so a failed push leaves the working pair untouched. Nodes without saved SSH
  credentials are refused with an actionable message.
- **Backup archives can leave the environment snapshot behind.** Each archive
  still contains the service's `STREAMFORGE_*` values — a disaster restore on
  a fresh server needs those keys to decrypt saved SSH passwords, Panel
  passwords and the backup passphrase. Set `STREAMFORGE_BACKUP_INCLUDE_ENV=0`
  to drop the snapshot; the manifest records the exclusion.
- **The signing key is checked at startup.** A missing `STREAMFORGE_SECRET_KEY`
  (or the published development default) is written to the log as an error,
  because anyone who knows that value can forge Panel session cookies.
- **Fresh installs provision the Panel password vault key**
  (`STREAMFORGE_PANEL_PASSWORD_VAULT_KEY`), and password changes fall back to
  hash-only storage when the key is absent, so the published installation
  default password can always be rotated. SMB backup destinations and
  credentials are validated, closing command injection through a destination.
- Fixed a defect where a denied permission rendered a 500 page instead of the
  access-denied page, and the XSS reachable through category, role, node and
  update confirmation dialogs.

## Installation

Requires installed Main v12.81 (or v12.82 for a safe reinstall). Update older
servers in order. Download and SHA256-check the official release ZIP, then
run:

```bash
streamforge-update --force /root/streamforge-12.82.zip
```

> **Update ZIP rebuilt (2026-10-27).** The first v12.82 update ZIP patched the
> sources but did not restart the Main HTTP workers, so the Panel kept showing
> v12.81 until a manual restart. The current ZIP restarts them as part of the
> update. If you already updated from the first ZIP, either run
> `sudo systemctl restart streamforge streamforge-public` once or re-run the
> command above with the current ZIP (reinstall is safe).

The updater patches the Main sources in place from exact-text hunks
(`scripts/apply_v1282_hardening.json`): every anchor is verified in a staged
copy first, and an unexpected tree refuses the update with nothing written.
Backup goes to `/var/backups/streamforge/v1282-<timestamp>/`, and a failure
after the write rolls every file back. Then **`streamforge` and
`streamforge-public` restart** so the new code is live at once and the Panel
shows v12.82; the channel supervisor, Nginx and live streams keep running.
The bundled Node Agent is byte-identical to v12.81 and is only restored when
an installed tree carries something else — **Remote Nodes do not need an
update for this release.**

Afterwards, open **Roles & Permissions** to review `sessions.kill` on
read-only roles, and check the log for the secret-key error.
